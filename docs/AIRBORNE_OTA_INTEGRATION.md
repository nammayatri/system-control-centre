## 1. Executive summary

Airborne is Juspay's OTA-update platform: SDKs (Android/iOS/RN) pull JS bundles + config from `airborne_server`, and a Next.js `airborne_dashboard` manages orgs, apps, files, packages, releases, and staged rollouts. We want that management surface inside SCC, next to Mobile Releases, under SCC's login and RBAC.

**Recommendation: BFF proxy through the SCC Haskell backend (Option A below).**
SCC backend gets a new `Products/AirborneOta/` module whose Servant routes mirror the ~25 airborne endpoints the UI needs, each guarded by `Protected 'OTA_*` RBAC. The proxy authenticates to airborne with a **service-account PAT** (`POST /api/token/issue` → cached ~5-min bearer token). The SCC frontend gets a new `products/airborne-ota/` module rebuilt from the dashboard's page inventory using SCC's own UI kit. The browser never talks to airborne directly.

Why this wins (details in §5):

- **Zero changes to airborne_server.** No fork, no CORS PR, no ingress surgery. Airborne's `/api/token/issue` PAT-exchange endpoint is purpose-built for machine callers.
- **One login, one RBAC.** SCC's entire value proposition is a single control plane; Option A keeps every OTA action behind the SCC session and permission model.
- **It matches SCC's existing service-account posture.** Play Console, App Store Connect, and GitHub App are already integrated as machine credentials held by the backend; `Products/Autopilot/Sync.hs` already does config-driven base URL + auth header + audited request/response against a remote cluster. The OTA proxy is the same shape.
- **The dashboard is trivially portable.** Every page is already `"use client"`; there are no Next API routes, no server actions, no cookies, no websockets, no browser file uploads. It is a de-facto SPA whose only server dependency is a same-origin path proxy — which the BFF replaces.

Two costs to accept with eyes open:

1. **Per-user attribution inside airborne collapses to the bot identity.** Compensations: SCC audits every proxied mutation with the SCC actor (§5.4), and the proxy stamps the actor into Superposition's `change_reason` on ramp/conclude/discard, which recovers per-user attribution in the upstream experiment audit trail.
2. **SCC RBAC becomes the *only* authorization gate on production traffic ramps**, backed by a standing org-admin credential. An SCC compromise or RBAC bug is a full-admin compromise of airborne. This is the same trade we already made for Play/ASC/GitHub; it is stated here so it is chosen, not stumbled into.

⚠️ **Phase-0 gate (blocking precondition):** the entire auth-bridging recipe in §5.1 works **only when the target airborne deployment runs `AUTHN_PROVIDER=keycloak` with signup and password grant enabled**. Bot signup and password-PAT minting are hard-disabled on the okta/auth0/oidc providers, and the OAuth fallback requires an interactive browser SSO login as the bot — often impossible under corporate SSO. Confirm the deployment's provider **before** committing to this design (§7 Q1).

## 2. Airborne architecture (what we learned)

### 2.1 Components

```
airborne repo
├── airborne_server             Rust/Actix, port 8081 — the control-plane API (KEEP, unmodified)
├── airborne_dashboard          Next.js 15 UI, port 3000 — what we REPLACE
├── airborne_analytics_server   Separate Axum binary, port 6400 — adoption/perf metrics
├── airborne_cli                Uploads files/bundles (multipart) — untouched by this project
└── SDKs (android/iOS/RN)       Call public /release/* + /build/* endpoints — untouched
```

### 2.2 airborne_server essentials

- **Routing:** everything admin-facing is mounted under `SERVER_PATH_PREFIX` (default `api` → `/api/...`, `src/main.rs:511`, `src/config.rs:175`). Only the SDK-facing `/release/*` and `/build/*` are at the root. Note: airborne's own `API_DOCUMENTATION.md` omits the `/api` prefix and is stale in places (wrong error format, missing whole modules — token, authz, file upload, release update/discard). Treat `src/main.rs` route mounting as truth.
- **Tenancy:** `organisation → application`, both referenced **by name** via headers: `Authorization: Bearer <JWT>` + `x-organisation` + `x-application` (`src/middleware/auth.rs:131-167`). Wrong org/app for your access → 403. Note the middleware never falls back from org role to app access — app-scope requests need a materialized app-level membership (relevant to bot setup, §5.1).
- **AuthN:** pure IdP passthrough — airborne never signs its own JWTs. `AUTHN_PROVIDER` ∈ keycloak (default) | oidc | okta | auth0; `OIDC_ISSUER_URL/CLIENT_ID/SECRET` are required at boot. Password login (`POST /api/users/login`) and signup work **only** with the Keycloak provider. Access tokens live ~300s (dev realm); **there is no refresh endpoint** — the stock dashboard just logs you out on 401.
- **AuthZ:** Casbin policies in airborne's own Postgres (not Keycloak groups). Subject = **lowercased email claim** — tokens without email are rejected. Roles: `super_admin > owner > admin > write > read`, enforced per-endpoint by an `#[authz(resource, action, org_roles, app_roles)]` proc macro. Org `admin` passes every release/package/file/config/dimension/cohort endpoint we need (verified against the `#[authz]` annotations); the only owner-only route is org ownership transfer, which we drop.
- **Machine auth (the linchpin):** Personal Access Tokens. `POST /api/token` (authed, needs the user's password) stores an AES-encrypted **offline refresh token** and returns `{client_id, client_secret}`. Then `POST /api/token/issue` — **public, no auth header** — exchanges `{client_id, client_secret}` for a fresh ~5-min access token (`src/token.rs:281-323`). The token impersonates the PAT's owner with that user's Casbin roles. PAT lifecycle caveats in §5.1.
- **Hard external deps:** Postgres, an OIDC IdP (Keycloak in practice), **Superposition** (each application = a Superposition workspace; releases are Superposition *experiments* — ramp/conclude/discard drive experiment traffic), S3 (+ optional CloudFront invalidation, optional Redis, optional KMS).
- **Errors:** uniform `{"code": "AB_00x", "message": "..."}` (AB_001=404, AB_004=401, AB_005=400, AB_006=403, AB_007=409). Success bodies have **no** uniform envelope; lists are typically `{data, total_items, total_pages}`. Every response carries `x-request-id`.
- **No CORS anywhere** in the server (no `actix-cors` dependency at all). The stock dashboard survives only because it is same-origin: dev-mode Next rewrites proxy `/api|/release|/build → backend` and `/assets|/builds → S3`; in prod an external reverse proxy does the same.

### 2.3 airborne_dashboard essentials

- Next.js 15 App Router, React 19, Tailwind 4, shadcn/Radix, SWR — but **every page is `"use client"`**; zero API routes, zero server actions, zero cookie/session logic. `middleware.ts` only sets security headers (CSP, `X-Frame-Options`, etc.) — no session or routing logic. Nothing about it is meaningfully "server-rendered".
- One fetch wrapper (`lib/api.ts`): prefixes `/api`, attaches `Bearer` + `x-organisation` + `x-application`, token in localStorage, 401 → clear + redirect to login, 403 → not-found page. Some calls add `x-dimension: dim1=v1;dim2=v2` for dimension-scoped queries.
- UI permission gating calls `POST /api/authz/me/enforce-batch` per page (batch "can I do X" checks) — under the BFF this is replaced by SCC permissions.
- Analytics is a separate raw-fetch path: `GET /analytics/adoption|performance|active-devices` on the analytics server — **unauthenticated, permissive CORS**.
- **No browser file upload**: "Create File" registers a URL over JSON. Multipart upload endpoints exist on the server but only the CLI uses them.

Release model worth internalizing: a release = Superposition experiment with `control` and `experimental` variants. **Ramp** = set traffic %, **conclude** = pick the experimental variant as winner, **revert** = conclude choosing `control`, **discard** = abandon. Ramp/conclude accept an optional `change_reason` that lands in Superposition's experiment audit trail (`release.rs:1029-1034, 1119-1125`) — we exploit this for attribution (§5.4). Release creation enforces **one ongoing release per dimension set** (`release.rs:392-403`) — this constrains the create-wizard phasing (§8).

## 3. SCC architecture recap (the integration surface)

- **Frontend:** one registry entry (`frontend/src/products/registry.ts`) auto-wires routes, sidebar, launcher tile, breadcrumbs. Product folder = `products/<name>/{api.ts, hooks.ts, types.ts, pages/, components/}`. Data via react-query v5 + axios `apiClient` (Bearer `sc_token`), toasts via sonner, permission gating via `ProtectedRoute` / `PermissionGate` / `usePermissions`. Product context lives **in the URL** (e.g. mobile's `groups/:groupId`), not in localStorage.
- **Backend:** a product = Permission ADT (`Products/<P>/Types/Permission.hs` with `KnownPermission` instances) + `Routes.hs` mounted in `Core/Server.hs`, plus extending `ProductSlug`, the `Permission` union, `productSlugToText`/`textToProductSlug`, `permissionToText`, `allPermissions`, `isViewPerm`, and `isManagerRestrictedPerm` in `Products/Types.hs` (all `-Wall` exhaustiveness-checked; `defaultPermissions` is generic and picks new cases up automatically). *(Note: `Products/Registry.hs` is a dead stub slated for removal, and `Manifest.hs` doesn't exist — CLAUDE.md's product recipe is stale; the real pattern is the above.)*
- **External HTTP:** one shared pooled client `Core.Http.Client` (`httpJson`/`httpRaw`, retry + 30s timeout). Two token-cache precedents exist — ASC (`Apple.hs:372-387`, IORef + 180s reuse floor) and GitHub App (`Github/Auth.hs:102-121`, MVar) — neither single-flight (benign double-mint for them); the single-flight precedent is `refreshInflight` in `Mobile/StoreSync.hs:1604`. Cross-cluster `Sync.hs` is the closest analogue overall: config-driven base URL, API-key header, every request/response audited.
- **No reverse-proxy machinery exists** (no Servant `Raw`, no streaming, no multipart) — and none is needed (§2.3: no browser uploads, no websockets).
- **Config:** base URL + secrets as env vars via `Core/Config.hs` + `Core.Secrets` (`lookupEnvSecret`); runtime-tunable knobs in `server_config`.

## 4. Options considered

### Option A — BFF proxy through SCC backend (RECOMMENDED)

Browser → SCC backend (`Protected 'OTA_*`) → airborne_server (service PAT).

- ✅ No airborne changes; no CORS problem (server-to-server); airborne creds never reach the browser; SCC RBAC + audit uniformly applied; the 5-min token is cached and re-issued server-side, invisible to users; frontend keeps using the one `apiClient` it already has; consistent with the existing Play/ASC/GitHub service-account posture.
- ❌ Every endpoint hand-declared in the proxy (~25 for full parity — mitigations in §6.2); airborne-side attribution collapses to the bot user (mitigated via `change_reason`, §5.4); SCC RBAC becomes the sole authorization gate over prod ramps (§1); one extra hop (irrelevant for an admin UI).

### Option B — Browser-direct with per-user airborne JWTs

SCC frontend logs each user into airborne and calls it with a second token. Steelmanned fairly: airborne's Keycloak supports **federated corporate IdPs** (`kc_idp_hint`, `enabled_oidc_idps`) — so "double login" can be a one-click SSO redirect, the user directory administers itself through federation, and the 5-minute token cliff is solvable with standard silent re-auth (`prompt=none`). Per-user attribution inside airborne is preserved — this is B's genuine advantage.

- ❌ The irreducible costs: **airborne_server has no CORS**, so browser-direct requires either an airborne change (add `actix-cors`) or co-locating both apps behind one shared ingress; a second axios instance with its own 401 policy (SCC's `apiClient` interceptor hard-logs-out of SCC on any 401 — airborne token expiry would nuke the SCC session); two RBAC systems administered in parallel (every operator needs correct Casbin roles in airborne *and* SCC permissions); and if OIDC redirect login is used, airborne's `PUBLIC_ENDPOINT` must point at SCC's origin, which also drags `/assets`, `/builds`, `/release` routing into SCC's ingress (it is the file-URL and SDK-URL base too — triple-purposed).
- **Verdict:** B is viable, not strawman-bad. A wins on consistency: SCC already fronts Play/ASC/GitHub with backend-held machine credentials and unified RBAC, and B's ingress/CORS coupling plus dual-RBAC administration is a permanent tax for attribution we can mostly recover via `change_reason`.

### Option C — Hybrid: proxy control-plane, browser-direct analytics

The analytics server already has permissive CORS and no auth, so the UI *could* call it directly. Rejected as the default: exposing an unauthenticated metrics endpoint to the browser advertises its URL, and proxying its 3 read endpoints through SCC costs ~50 lines while adding RBAC in front of an otherwise-open service. (Keep as an escape hatch if analytics payloads ever get heavy.)

### Option D — iframe-embed the existing Next dashboard

Dead on arrival: the dashboard sends `X-Frame-Options: DENY` and `frame-ancestors 'none'` itself, and it would keep its own login. Not pursued.

### 5.1 Auth bridging

**Precondition (Phase-0 gate, see §1):** target deployment must run `AUTHN_PROVIDER=keycloak` with signup + password grant enabled. All steps below are Keycloak-only. *(Verified for `airborne.juspay.in`, §7 Q1.)*

> **Status 2026-07-17: enrolment DONE** — the bot's PAT has been generated and its `client_id`/`client_secret` are in hand. Remaining before Phase 1: (a) store them as SCC secrets `SC_AIRBORNE_PAT_CLIENT_ID` / `SC_AIRBORNE_PAT_CLIENT_SECRET_B64` (k8s `stringData` must hold the **base64 of the value** per the existing SC_*_B64 convention — a raw value yields "credentials not configured"); (b) smoke-test `POST /api/token/issue` with them; (c) verify the bot's org grants cover **both** orgs (`movingtech` AND `driver`, §7 Q2) — a PAT minted in one org's context still impersonates the bot everywhere, but the bot needs admin membership in each org it will operate on; (d) vault the bot's password for the re-enrolment runbook.

**One-time enrolment per environment (for reference / re-enrolment):**

1. **Provision a bot user** — `POST /api/users/create` (unauthenticated; provisions into Keycloak via the server's admin client; requires `first_name`/`last_name`/`email`). ⚠️ **Register the bot with its email as the Keycloak username** (`name == email`, e.g. `scc-bot@nammayatri.in`): `POST /api/token` later 401s with "Username mismatch" unless the PAT `name` equals the token's email-derived username *and* works as the Keycloak login username (`token.rs:60-80`).
2. **Grant org access** — `POST /api/organisation/user/create {user: <email>, access: "admin"}` (binds Casbin by email, works before first login). **Ordering matters:** the org and at least one application must already exist; the org-admin grant materializes app-admin rows on all apps existing *at grant time*, and apps created later via `/organisations/applications/create` auto-fan-out to org admins. Drift edge: if someone removes the bot from one app's user list, the proxy 403s for that app even though org-admin remains.
3. **Mint one PAT** — login as the bot, `POST /api/token {name: <email>, password}` with `x-organisation` + `x-application` headers (an app is required by the endpoint) → `{client_id, client_secret}`. Store as SCC secrets (`SC_AIRBORNE_PAT_CLIENT_ID`, `SC_AIRBORNE_PAT_CLIENT_SECRET_B64` — remember the k8s `stringData` base64 convention).

**Steady state:** SCC backend calls the **public** `POST /api/token/issue {client_id, client_secret}` → `{access_token, expires_in≈300}`. Cache in a module-level cache with expiry, refresh ~30s early — adapted from the two existing token caches (ASC: IORef + 180s reuse floor, `Apple.hs:372-387`; GitHub App: MVar, `Github/Auth.hs:102-121`). Neither implements single-flight; add a `refreshInflight`-style MVar (`StoreSync.hs:1604`) so concurrent misses don't stampede `/token/issue`.

**PAT lifecycle (do not skip — silent-death modes):**

- The stored credential is a Keycloak **offline refresh token** with a **30-day idle expiry** (`offlineSessionIdleTimeout=2592000`). On-demand refresh alone means a quiet month kills the PAT and the whole product 401s until manual re-enrolment. **Mitigation: a daily keepalive** — a `forkFlow`/scheduler tick that calls `/token/issue` and alerts (Slack) when re-issue fails after retry.
- Airborne's `issue_token` returns the IdP's rotated refresh token but **never re-persists it** (`token.rs:317-322`). Pin in deployment notes: the realm must keep `revokeRefreshToken=false` (its current default) and offline idle ≥ 30d, or `/token/issue` breaks permanently after the first refresh.
- `DELETE /api/token/{client_id}` only deletes airborne's DB row — the Keycloak offline session survives. Real revocation = delete the PAT **and** revoke the bot's offline session in Keycloak. Conversely, Keycloak-side user-disable kills the PAT with no airborne-side signal.
- Keep a **re-enrolment runbook** (requires the bot's password — store it in the vault, don't rotate it away). The runbook is **manual by design**: the bot password must never be storable/readable by SCC (else SCC compromise = unlimited PAT minting), and SCC writing its own k8s secret + self-restarting is a privilege widening we don't want. Runbook: vault password → `POST /api/users/login` as bot → `POST /api/token` (org/app headers) → new `{client_id, client_secret}` → update k8s secret (base64-of-value in `stringData`) → restart → `DELETE /api/token/{old_client_id}`. *Future option if rotation ever becomes routine:* an admin-only "re-enrol PAT" page where the admin types the bot password ephemerally and SCC performs the API dance, displaying the new credentials once for manual k8s update — assists without storing.

*Alternative steady state (rejected):* calling `POST /api/users/login` with the bot's password per cycle avoids PAT lifecycle entirely, but each login mints a fresh Keycloak SSO session (~hundreds/day of session pollution) and keeps a raw password in steady-state use. PAT is the right call.

### 5.2 Backend module (`backend/src/Products/AirborneOta/`)


- **Permissions (proposed):** `OTA_VIEW`, `OTA_RELEASE_CREATE`, `OTA_RELEASE_RAMP`, `OTA_RELEASE_CONCLUDE` (covers revert), `OTA_RELEASE_DISCARD`, `OTA_PACKAGE_MANAGE`, `OTA_FILE_MANAGE`, `OTA_CONFIG_MANAGE` (properties/dimensions/cohorts/views), `OTA_APP_MANAGE` (application create). ### 5.3 Frontend module (`frontend/src/products/airborne-ota/`)

Registry entry: `slug: 'airborne-ota'`, `label: 'Airborne OTA'`, `basePath: '/airborne'`, `viewPermission: 'OTA_VIEW'`, nav = Releases / Packages / Files / Config (dimensions+cohorts+properties+views under one section). ### 5.4 Audit & attribution

Two layers, both mandatory:

1. **SCC-side:** every proxied mutation logs an `airborne_events` row with `"actor" .= apEmail ap`, the airborne endpoint, request summary, upstream status, and airborne's `x-request-id` (for correlation with airborne/CDN logs) — same convention as mobile (`Mobile/Handlers/Rollout.hs`) and `Sync.hs`. ### 5.5 Per-app access control (SCC-side)

Airborne's own per-app roles are bypassed by the bot (org-admin everywhere), so app-level access is enforced in SCC — reusing the **deployment-access** machinery Mobile Releases already runs on.

**App identity — live off airborne, no local mapping (2026-07-20 rewrite).** The `airborne_app_map` indirection was **removed**; migration `0045-airborne-ota.sql` now creates the final shape directly (audit trail keyed on `airborne_org`/`airborne_app`, no mapping table). Rationale: airborne applications are **immutable-named** (the only application route is `POST /create` — no rename, no delete; the `v2`/`v3` suffixes are *new* apps, not renames), so there is no upstream rename to protect against, and a curated SCC slug was mostly ceremony for this integration. The product is now driven **live off the bot's `/api/users` app tree**, keyed on a **composite ref `<org>~<app>`** — the airborne `x-organisation`/`x-application` pair. That ref is the identity everywhere: the URL `:app` segment (`/airborne/movingtech~nammayatriv2/...`), the RBAC grant key (`sc_person_deployment_access.app_group`), and the audit key (`airborne_events.airborne_org` + `airborne_app`). `resolveApp` splits the ref in-process (no DB); `GET /airborne/access` lists the caller's OTA_VIEW-granted apps live (batched RBAC via `computeEffectivePermissionsForAppGroups`), `GET /airborne/apps` (product-level `OTA_APP_MANAGE`) lists the full fleet for the admin grant-picker. Consequences: a new airborne app appears in SCC on its own (no map step); apps are shown by their **raw airborne name** (which may be a slug like `nammayatriv2` *or* a display name with spaces like `Chennai One - Debug` — both round-trip: `encodeURIComponent` → Servant decode → split on `~` → `x-application`, verified 200 against the live fleet); the full bot-visible fleet is shown incl. debug/sandbox (deliberate — "show every app the bot can see"); if airborne is unreachable the list is empty with `upstreamReachable:false` (no offline cache). **Trade-offs accepted:** an app-name containing `~` would mis-split (no current app does — monitorable assumption); there is no per-app override table (hide/relabel a specific app would need a small *optional* overrides table). During development an interim migration re-keyed slug-based grants + audit to `<org>~<app>` via the map; that step was folded away when the migrations were collapsed, since no environment had shipped the slug-keyed shape.

The access-control machinery itself:

- **Data:** one row per grant in the existing `sc_person_deployment_access` table (`person_id`, `product_slug='airborne-ota'`, `app_group=<org>~<app>`, `role_id`) — migration `0041-deployment-access.sql`; managed through the existing admin UI like mobile's app-group grants (grant picker fed live from `GET /airborne/apps`, never free text). `app_group` is an opaque per-product TEXT label (no FK) whose meaning each product defines — autopilot already uses two meanings under one slug (backend service groups vs `app_catalog` names like `NammaYatri`/`Cumta`) — and every read is keyed by `(product_slug, app_group)`, so `airborne-ota` rows are a disjoint namespace: granting OTA "NammaYatri" neither grants nor collides with mobile's "NammaYatri", and autopilot semantics are untouched.
- **Resolution semantics** (existing, `Core/Auth/Queries.hs:277-290`): a deployment row for (person, ota, app) **overrides** with that row's role; absent a row, permissions **fall back to the person's product-level OTA role**; no product row either → empty. So: *leads/admins* get one product-level row (all apps, no per-app bookkeeping); *scoped operators* get NO product-level row and only per-app deployment rows — they see and touch nothing outside their grants. The override direction also allows per-app demotion (product Admin + Viewer row on app X = Viewer on X).
- **Backend enforcement, two layers:** the route's `Protected 'OTA_*` coarse gate (passes for deployment-only users via `hasAnyDeploymentPermission`, as mobile does), then first line of every `:app`-captured handler: `requireDeploymentPermission (Proxy :: Proxy 'OTA_RELEASE_RAMP) ap app` (`Core/Auth/Protected.hs:249-263`) — the URL's app segment is enforced server-side, never just filtered in the UI.
- **App-list filtering:** `GET /airborne/access` intersects the bot's airborne app list with the caller's effective perms — return only apps where `computeEffectivePermissionsForAppGroup pid "airborne-ota" app` contains `OTA_VIEW`, alongside each app's permission set so the frontend gates buttons without extra calls.
- **Frontend:** app selector renders only the filtered list; deep links to ungranted apps hit the route guard; `<PermissionGate product="airborne-ota" permission="OTA_RELEASE_RAMP" appGroup={app}>` hides per-app actions — all existing components.

> **TODO (future, independent of OTA) — close the same gap in Mobile Releases.** Audit finding 2026-07-17: app-level access is *not* actually enforced for mobile today. The `Mobile/` handler subtree has **zero** `requireDeploymentPermission` calls (rollout pause/resume/update, store sync, groups, revert, dispatch are product-level only — any autopilot-permission holder can operate every brand), and the admin grant picker offers only `deployment_config` app groups (`releases/api.ts:576-580`), so mobile-app-scoped rows can't even be created via the UI. The only app-enforced mobile path is the shared lifecycle actions in `Actions/Release.hs` reached through `ReleaseSummary`. Fix recipe when picked up: `requireDeploymentPermission` at the top of every `Mobile/Handlers/*` mutation (appGroup = `app_catalog` name) + add `app_catalog` names to the grant picker + `appGroup`-scoped `PermissionGate`s on the mobile pages. The OTA product (this doc) must NOT inherit this gap — §5.5 wires enforcement and the picker from day one.

**New-app lifecycle (out-of-band creation upstream).** Detection is automatic: airborne fans out app-admin to org admins on every `create_application` (`casbin.rs:1391-1394`), so a new app in either org appears in the bot's access map (`GET /api/users`) immediately — no airborne-side action needed. It then flows: (1) the proxy's upstream fetch sees it immediately — **no mapping step**; (2) it appears at once in the admin grant-picker (`GET /airborne/apps`, product-level `OTA_APP_MANAGE`); (3) regular users still see nothing until granted — `GET /airborne/access` only returns apps where the caller's effective perms include `OTA_VIEW`, and direct requests to an ungranted app fail closed at `requireDeploymentPermission`; (4) an admin adds deployment-access grants keyed on `<org>~<app>`, at which point it appears for those users. So onboarding a new app is now a **pure RBAC action** — there is no row to author and nothing to keep in sync. Renames/deletions need no reconciliation either: airborne applications are immutable-named (create-only), so a "rename" is simply a new app that shows up on its own, and the old ref's grants become inert.

## 7. Open decisions (need product/infra input)

1. **Which airborne deployment — and its `AUTHN_PROVIDER`?** *(Phase-0 blocker, §1.)* Juspay-hosted vs self-hosted determines whether we can provision the bot at all and who owns Keycloak/Superposition ops. **Partially answered 2026-07-16:** the hosted instance's public discovery endpoint (`GET https://airborne.juspay.in/api/dashboard/configuration`) reports `authn_provider: keycloak`, `password_login_enabled: true`, `registration_enabled: true` — the §5.1 recipe works there. Caveat: `organisation_creation_disabled: true`, so the org must be requested (`POST /api/organisations/request` → Juspay's sheet) or provisioned by the airborne team; remaining decision is hosted-vs-self-hosted.
2. **Single org or multi-org?** **Answered 2026-07-17 (repo + live probe): there are TWO orgs on the hosted instance** — `movingtech` (consumer apps) and `driver` (provider apps), both on `airborne.juspay.in` (the committed provider sandbox URL `airborne.sandbox.juspay.in` is dev-env only; `driver` serves on prod too). Consequence: `x-organisation` is NOT a fixed config value — it is the **org half of the composite ref** `<org>~<app>`, split in-process by `resolveApp` (no DB lookup). One bot user granted admin in both orgs still suffices (the token impersonates the user across orgs; the header selects per request), but enrolment (§5.1) must run the org-grant step for each org.
3. **Are dimension-targeted releases in use today?** If yes, a minimal targeting step (raw key-value dimension entry) must ship with the Phase-2 wizard, not Phase 3 — otherwise the one-ongoing-release-per-dimension-set guard makes the wizard unusable for those apps (§8).
4. **Application onboarding**: in-product (`OTA_APP_MANAGE` + create-app proxy) or out-of-band (CLI/curl runbook)? Cheap either way; decide before Phase 1 nav is final.
5. **Analytics in MVP?** The tab is cheap (GET passthroughs) but only meaningful if the analytics pipeline is actually deployed for our apps. **Answered 2026-07-21 (code audit + live probe): there is NO analytics data today, and the tab cannot show any until a producer is written.** Two independent blockers: (a) **nothing emits events** — the SDKs have no analytics HTTP client at all, only a host-app callback that defaults to a no-op (`AirborneInterface.kt:19` is an empty `onEvent`; iOS's is `@objc optional`), and the NammaYatri app implements neither, so a repo-wide grep for `analytics/events` finds only the route registration itself (`main.rs:120`); (b) **`SC_AIRBORNE_ANALYTICS_URL` is unset** (empty default, `Core/Config.hs`), so the tab renders the calm "not available" state rather than zeros. Live probe of `airborne.juspay.in/analytics/health`: `status:"healthy"` but `clickhouse:false`, `events_processed_last_hour:0`, `storage_size_gb:0.0`; `/analytics/active-devices` for a real app returns `total_active_devices:0, daily_breakdown:[]`. Beware: **empty-store reads are zero-filled inside a `success:true` envelope**, so "working but empty" is byte-identical to "working with data" — zeros carry no diagnostic signal. Additional upstream defects that will each independently produce zeros *after* those two are fixed: `/analytics/performance` is a hardcoded stub; adoption coerces a missing `release_id` to the literal `"default"`; the rollback SQL matches `'rollback_triggered'` while the enum emits `ROLLBACK_INITIATED/…`; `failure_rate` is `100 if any else 0`; the kebab-case `LOGGING_INFRASTRUCTURE` values in the shipped `.env` files don't parse (so ClickHouse can't be selected and the server silently runs the in-memory VictoriaMetrics path); and CloudFront fronting the public host **ignores the query string** on `/analytics/*`, so pointing SCC at the public hostname would show one app's numbers under every app — use a direct origin.
6. **Permission granularity** — is the §5.2 set right, or should ramp/conclude/discard collapse into one `OTA_RELEASE_OPERATE`? **Answered 2026-07-21: keep the three separate — the split is load-bearing.** `Manager` is *defined* by the discard boundary: `defaultPermissions Manager = filter (not . isManagerRestrictedPerm)` and `isManagerRestrictedPerm (OtaPerm p) = p elem [OTA_RELEASE_DISCARD, OTA_APP_MANAGE]` (`Products/Types.hs:101,115-116`). Collapsing them leaves only two bad options: include `OPERATE` in Manager (managers gain the kill switch — the one thing the role exists to withhold) or exclude it (managers lose ramp+conclude and become near-Viewers). Separate permissions are what let day-to-day rollout duty be delegated without handing over release destruction. **Also note this was never a go-live gate:** role→permission sets are computed in code, not stored — the DB holds only role *names* — so a later change costs one ADT edit (`-Wall` catches every case) plus 5 string occurrences in one frontend file (`ReleaseDetail.tsx`); the only data caveat is `sc_person_permission_override`, which stores permission text, so any override naming a removed permission would silently stop applying.
8. **Mobile↔Airborne per-app cross-link** *(Phase 4, deferred).* There is **no deterministic join** between an `app_catalog` row and an airborne app: the mobile release context's `ota_namespace` field is dead (always `Nothing` at all construction sites), and the only observed correspondence is a **naming convention** (airborne app name ≈ `toLower(name)` with a `-ios` suffix and org `driver` for provider) that is coincidental — several `app_catalog` apps have no airborne app at all, and airborne names drift (`nammayatriv2`, `bharattaxiv2`, display names with spaces). Phase 4 therefore ships a **product-level** cross-link (OTA app Overview → `/mobile/releases`), not a per-app deep link. For a deterministic per-app link (either direction), add an explicit stored mapping — preferred: `ALTER TABLE app_catalog ADD COLUMN airborne_app_ref TEXT` (nullable; holds the `<org>~<app>` ref; null = no OTA app) — then wire the reverse link on the Mobile side. Until then, do **not** key any cross-link on `ota_namespace` or the naming convention.
9. **App-mapping granularity** (§5.5) — **Answered 2026-07-17: one airborne application per brand+platform** (android namespaces bare, iOS `-ios` suffixed), with env variants only for Cumta (`chennai-one-debug*`) and version-migration suffixes on some (`nammayatriv2`, `bharattaxiv2`, `lynxv2`). Live probe of the public `/release/{org}/{app}` endpoint (2026-07-17): **18 consumer namespaces serve under `movingtech`** (nammayatriv2±ios, chennaione±ios, chennai-one-debug±ios, odishayatri±ios, yatrisathi±ios, keralasavaari±ios, bridge±ios, bharattaxiv2/bharattaxi-iosv2, lynxv2/lynxiosv2) and **4 provider namespaces under `driver`** (nammayatri, yatrisathi, keralasavaari-ios, bharattaxi) — ~22 live apps total. Referenced in code but 404 (not yet created, or no live release — indistinguishable without credentials): manayatri±ios and yatri±ios in both orgs, plus most provider namespaces. So airborne apps are N:1-ish with `app_catalog` rows per platform, and the **org half of the ref is load-bearing** (Q2) — the same app name can exist under both `movingtech` and `driver` (e.g. `yatrisathi`), so an app is only unambiguous as `<org>~<app>`. Note the live fleet is shown in full (incl. debug/sandbox) straight from the bot's app list, so this enumeration is descriptive, not a configured allow-list.

The other eight Phase-3 mutations have no such field: the five that reach Superposition hardcode their own reason string server-side (`dimension.rs:123,161`, `cohort.rs:244,345,531`, `properties.rs:200,240,…`) and the three release-view handlers write airborne's own `release_views` table, which has no audit column at all. So the "8 unstamped mutations" is an **upstream limitation, not an SCC gap** — stamping them would be silently discarded (no `deny_unknown_fields` anywhere in airborne_server) and would falsely read as working attribution. SCC's own `airborne_events` trail is the compensation, and is now readable in-product (Phase 8). **Key contract learnings:** dimension list/cohort-priority/properties-list status codes are unreliable (Superposition failures flatten to 500, never 404/409 — a client can't distinguish "not found" from "server error" by status alone); properties `PUT /schema` is **full-replace** (omitted keys are deleted upstream — the page keeps a local draft gated on a "seeded" flag so a slow/failed initial fetch can never full-replace-delete everything); `x-dimension` is a naive `k=v;k2=v2` string with no escaping (';' in any dimension/cohort/view value corrupts it — rejected at input time everywhere it's built); "release-view" collides with upstream's dimension sub-router and is rejected as a dimension name both client- and server-side; cohort/dimension reorder mirrors the airborne dashboard's own `position ± 1` / one-`{name: index}`-per-call approach exactly (verified against dashboard source, not just the API). Full `#[authz]` review confirmed no route lets a deployment-scoped grant reach a product-global effect. **To go live: PAT secrets** (§5.1) — as with Phases 1–2, these routes return "credentials not configured" until then.

**Phase 4 — analytics + polish** ✅ **done 2026-07-20** (adversarially reviewed across 3 lenses; 4 confirmed findings fixed, 3 refuted — backend RBAC lens found nothing)
Per-release **Analytics tab** on the release detail, restyled 2026-07-20 to mirror the airborne dashboard: header, range presets Last 24 hours / 7 days / 30 days **plus a custom range** (a calendar-popover `DateRangePicker` built on `@radix-ui/react-popover` — no new dependency; it re-stamps `dark` on the portaled content since Radix portals escape the scoped theme wrapper), interval auto-derived (HOUR ≤24h else DAY) over a midnight-based window, six metric tiles (Total Devices, Check for Update Rate, Average Download Time, Downloads, Applied Updates, Rollbacks) and four charts (Update Adoption Over Time, Update Success Rate, Time to Adoption, Rollback Activity) — all hand-drawn inline SVG (SCC has no chart library). Retained beyond airborne's own dashboard: version distribution and an update-failures table. **Upstream-health status banner** via a new registry `Banner` slot rendered in `ProductLayout` inside the theme wrapper: red when the control plane is unreachable, amber when analytics is configured-but-down, silent otherwise. **Mobile Releases cross-link** on the OTA app Overview (access-gated link to `/mobile/releases`).
Backend: 5 `OTA_VIEW` analytics routes under `:app/analytics/{adoption,versions,active-devices,failures,performance}`, plus `healthH` extended with a resilient `probeAnalyticsHealth`. **Analytics is a SEPARATE, unauthenticated host** (`SC_AIRBORNE_ANALYTICS_URL`, empty default) — so it uses a distinct `analyticsRequest` in `Client.hs` that sends **no PAT and no headers**, passing org/app as `org_id`/`app_id` **query params** (`analyticsScope`). Because it needs no PAT, analytics works even before the control-plane PAT secrets are set.
**Key contract learnings:** `performance` is a hardcoded upstream **stub** (always 0.0, ignores every param) — it is nonetheless proxied and surfaced as the "Average Download Time" tile so the tile lights up for free if airborne ever implements it; until then it reads `0.0ms` (airborne's own dashboard shows the same); `failures.failure_rate` is **degenerate** (100 if any failure else 0) — never shown as a rate; `active-devices.total_active_devices` is a **peak single-day** count, not a period sum (labeled "peak/day"); adoption **HOUR mode covers the current UTC calendar day only** (not a rolling 24h) and needs epoch-**millis** dates with **both** `start_date` and `end_date` (missing one silently defaults to epoch-0) — the "Today" preset is labeled honestly and the adoption timestamp is minute-quantized so tab-toggles reuse the react-query cache; the four sections use divergent upstream windows for the same preset (adoption takes interval+date, the others only a `days` lookback), inherent to the endpoints. The Analytics tab is decoupled from the release-body fetch (a failed release load no longer blanks it). **Mobile↔Airborne has no deterministic per-app join** (the `ota_namespace` field is dead/always-null; slug alignment is convention, not a stored FK), so the cross-link is a product-level bridge, not an asserted per-app mapping — a real per-app link would need an explicit stored column (see §7).
**To go live for analytics:** set `SC_AIRBORNE_ANALYTICS_URL` (until then the tab shows a calm "analytics isn't available for this environment"); the control-plane routes still need the PAT secrets (§5.1).

Explicitly **out of scope**: airborne org/app *user* management UI, PAT self-service UI, login/register/OAuth/onboarding pages, file upload, any airborne_server modification.
